# IcoGenX v2.0.0 Platform Plan

Audit date: 2026-05-25

## Vision

IcoGenX v2.0.0 turns the app from a set of individual real-time games into a scalable multiplayer platform for couples and friend groups. The release should make it easy to discover games, invite known friends without copying room codes, add new game engines through the Rust trait/registry system, and support 2-player today with a clear path to 3-4 player games.

## v2.0.0 Release Priorities

The release should focus on two outcomes:

1. Friends and invites are trustworthy enough to ship publicly.
2. Checkers proves that a new full game can be added through the platform architecture without bespoke lobby rewrites.
3. Drop Four chaos variants show the same platform can support vertical gravity games with board-wide physics events.

## Phase 5 Plan: Friends, Presence, and Invites

### P0 - Ship-Blocking Hardening

These items should be completed before marketing v2.0.0 as friend-invite ready.

#### 1. Verifiable WebSocket Identity

Current state: implemented. The frontend issues a signed identity token and the Rust backend verifies it before storing presence identity.

Plan:

- Add a Next.js API route that issues a short-lived signed social token for the logged-in user.
- Extend `ClientMessage::Identify` to send that token instead of raw trust-only identity.
- Verify the token in Rust before storing `player_users` and `user_connections`.
- Keep guest users out of friend/presence flows.
- Add tests for valid token, expired token, malformed token, and mismatched user claims.

Suggested payload:

```json
{
  "sub": "user_id",
  "name": "Display Name",
  "image": "https://...",
  "exp": 1760000000
}
```

#### 2. Authorized Friend Invites

Current state: implemented. The frontend issues a signed invite grant after checking accepted friendship, and the Rust backend verifies the sender, recipient, game type, and variant.

Plan:

- Add a signed invite grant issued by the Next.js app after checking the friendship in the DB.
- Extend `SendGameInvite` to include the grant.
- Verify in Rust that the sender, recipient, game type, and variant match the grant.
- Return an explicit ack/error to the inviter when the recipient is offline, not a friend, or the game type is invalid.
- Never create a room for an unknown `game_type`.

#### 3. Invite Lifecycle Registry

Current state: partially implemented. Invite IDs are tracked server-side and decline routing uses `invite_id` lookup instead of trusting the client-provided inviter. Expiry notification cleanup remains release polish.

Plan:

- Track active invites in Rust: `invite_id`, `from_user_id`, `to_user_id`, `room_code`, `game_type`, `variant`, `created_at`, `expires_at`, and status.
- Change decline handling to use `invite_id` only; look up the inviter server-side.
- Expire invites after a short window, such as 2 minutes.
- Reject accepts/declines for expired or unknown invites.
- Send `GameInviteAccepted`, `GameInviteDeclined`, and `GameInviteExpired` messages where useful.

#### 4. Presence Lifecycle Accuracy

Current state: implemented. Offline presence is debounced, room create/join/leave broadcasts current-room updates, and final-tab disconnects remove stale subscriptions.

Plan:

- Add the planned 5-second offline debounce so refreshes do not flicker friends offline.
- Broadcast `PresenceUpdate { current_room }` when a user creates, joins, or leaves a room.
- Remove stale `presence_subscriptions` entries when a user has no active connections.
- Support multiple tabs by keeping the user online until the final tab disconnects.
- Add tests for multi-tab connect/disconnect, room change updates, and debounce behavior.

#### 5. Friend API Authorization

Current state: implemented. Friend responses now distinguish recipient-only accept/decline, initiator cancel, and accepted-friend removal.

Plan:

- Only the request recipient can accept a pending request.
- Allow the initiator to cancel an outgoing pending request through a separate `cancel` action or endpoint.
- Allow either side to remove an accepted friend through a dedicated endpoint.
- Return stable error codes instead of raw error message text.
- Add API tests for self-add, bad code, duplicate request, recipient accept, initiator accept denied, cancel, decline, and remove friend.

### P1 - UX Completion

#### 1. Typed Frontend Social State

Current state: `friends` and several social payloads are typed as `any` in `GameContext`.

Plan:

- Add shared TypeScript types for friend list items and invite payloads.
- Replace `any[]` in context and components.
- Keep server JSON field names normalized at the boundary.

#### 2. SocialDock Grouping

Current state: accepted friends and incoming pending requests are shown. Outgoing pending is not separately displayed.

Plan:

- Group SocialDock into:
  - Online friends.
  - Offline friends.
  - Pending incoming requests with accept/decline.
  - Pending outgoing requests with waiting/cancel.
- Show room status only when the backend confirms `current_room`.
- Replace `alert()` calls with local toast/banner feedback.
- Disable invite actions while the websocket is disconnected.

#### 3. Metadata-Driven Invite Picker

Current state: `SocialDock` has a hand-maintained `inviteGames` array that duplicates catalog data and misses variants.

Plan:

- Drive invite choices from `GAME_CATALOG`.
- Exclude `isComingSoon` games from invite actions.
- Use `game.gameType` and variant IDs from metadata.
- Include future Checkers variants automatically.

#### 4. Accept Invite Routing

Current state: accepting an invite calls `joinRoom`, but routing depends on page-local effects and is not guaranteed from every page.

Plan:

- Route directly to `getGamePath(gameType, variant)` after accept.
- Preserve invite context while the room join is pending.
- Show a recoverable error if room join fails because the room expired or filled.

### P2 - Social Polish

- Add friend affordances from profile/likes/lobby surfaces after the core flow is secure.
- Add accessibility labels for social status and invite actions.

## Phase 7 Plan: Twist Checkers

Checkers is the v2.0.0 proof that the platform can absorb a substantial new game with multiple variants while keeping the backend authoritative.

### Game Identity

- Backend game type: `checkers`.
- Frontend catalog ID: `checkers`.
- Routes:
  - `/games/checkers`
  - `/games/checkers/classic`
  - `/games/checkers/anti`
  - `/games/checkers/zombie`
  - `/games/checkers/minefield`
  - `/games/checkers/vip`
  - `/games/checkers/portal`

### Backend Data Model

Add `backend/src/games/checkers.rs`.

Core state:

```rust
pub struct CheckersGame {
    board: Vec<Option<CheckerPiece>>,
    current_player: u8,
    variant: String,
    game_over: bool,
    winner: Option<u8>,
    must_jump_from: Option<usize>,
    setup_complete: [bool; 2],
    mines: [Vec<usize>; 2],
    vip_pieces: [Option<usize>; 2],
    portals: std::collections::HashMap<usize, usize>,
    last_event: Option<String>,
}

#[derive(serde::Serialize, serde::Deserialize, Clone, Copy)]
pub struct CheckerPiece {
    owner: u8,
    is_king: bool,
    is_vip: bool,
}
```

Implementation notes:

- Store the board as 64 squares, but validate that moves use playable dark squares.
- Keep all hidden setup data server-side and expose only the current player's own secrets in `state_for_player`.
- Use mandatory captures for Classic unless a variant explicitly changes the outcome, not the move legality.
- Track `must_jump_from` for multi-jump chains.
- Promote to king after landing on the opponent back row.

### Backend Actions

Client actions should remain inside the existing generic `GameAction` message.

```json
{ "game": "CheckersSecret", "mines": [17, 19, 21], "vip": 21 }
```

```json
{ "game": "CheckersMove", "from": 12, "to": 19 }
```

Validation:

- Reject actions from the wrong player.
- Reject setup actions outside the setup phase.
- Reject invalid square indexes, light squares, occupied destinations, backwards moves for non-kings, non-captures when a capture is available, and moves that break an active multi-jump chain.
- Return clear `Error` messages without leaking opponent secrets.

### Variant Rules

#### Classic

- Standard 8x8 checkers on dark squares.
- Forced captures.
- Multi-jump required while available from the landing square.
- Promotion on reaching the back row.
- Win by capturing all opponent pieces or leaving the opponent with no legal moves.

#### Anti

- Same movement and forced-capture rules as Classic.
- Win condition is reversed: lose all pieces or have no legal moves to win.

#### Zombie

- A jumped piece changes owner instead of being removed.
- Converted pieces keep king status unless tests show that produces poor balance.
- The jumper lands normally and the turn/multi-jump rules continue from the landing square.

#### Minefield

- Setup phase before play.
- Each player secretly places a fixed number of mines on valid dark squares.
- Landing on an opponent mine triggers an explosion, removes affected pieces, clears the mine, and emits `last_event`.
- Explosion radius should be deterministic and covered by tests.

#### VIP

- Setup phase before play.
- Each player secretly marks one owned starting piece as VIP.
- Capturing the opponent VIP ends the game immediately.
- State sent to each player reveals only their own VIP identity until it is captured or the game ends.

#### Portal

- Portal pairs are generated on valid dark squares in rows 3 and 4.
- Landing on a portal teleports the piece to its paired square and ends the turn.
- If the destination is occupied, the occupant is removed by telefragging.
- Portal layout is public and included in state.

### Backend Integration

- Add `pub mod checkers;` in `backend/src/games/mod.rs`.
- Register `checkers` in `backend/src/game_registry.rs`.
- Add registry tests for `checkers` and each supported variant.
- Add focused unit tests in `checkers.rs` for movement, forced jumps, promotion, each variant, setup privacy, and game-over conditions.

### Frontend Implementation

Add:

- `frontend/src/components/CheckersBoard.tsx`
- `frontend/src/components/checkers.module.css`
- `frontend/src/app/games/checkers/page.tsx`
- `frontend/src/app/games/checkers/[variant]/page.tsx` if route patterns stay variant-specific.

UI requirements:

- Select-to-move controls first; drag-and-drop can be added after the rules are stable.
- Highlight legal moves and mandatory capture source.
- Show setup UI for Minefield and VIP.
- Show public portal overlays.
- Show private mine/VIP markers only to the owning player.
- Use `GameFrame` for room, score, player strip, leave, and rules layout.
- Keep the board responsive with a fixed square aspect ratio.

Metadata:

- Add Checkers to `frontend/src/lib/gameMetadata.ts`.
- Include 6 variants: `classic`, `anti`, `zombie`, `minefield`, `vip`, `portal`.
- Add routes to `getGamePath` mapping if required by `GameContext`.
- Ensure SocialDock invite picker picks up Checkers through `GAME_CATALOG`.

### Checkers Definition of Done

- Classic Checkers can be played end-to-end by two players.
- All six variants have backend tests for their unique rule changes.
- Hidden setup data is not leaked through `state_for_player`.
- Frontend can select, submit, and render legal moves without layout shifts on mobile.
- Room creation, invite acceptance, and manual room-code join all work for Checkers.

## Phase 8 Plan: Drop Four Chaos

Drop Four Chaos is a vertical four-in-a-row game family inspired by tabletop gravity grids. It should use the same `Game` trait flow as other backend-authoritative games while making gravity, removal, hidden zones, and one-time powers clear in the UI.

### Game Identity

- Backend game type: `drop_four`.
- Frontend catalog ID: `drop-four`.
- Routes:
  - `/games/drop-four`
  - `/games/drop-four/classic`
  - `/games/drop-four/wrecking-ball`
  - `/games/drop-four/popout`
  - `/games/drop-four/gravity-flip`
  - `/games/drop-four/battleship-drop`
  - `/games/drop-four/heavy-token`

### Backend Data Model

Add `backend/src/games/drop_four.rs`.

Core state:

```rust
pub struct DropFourGame {
  board: Vec<Option<DropFourPiece>>, // 7 columns x 6 rows
  current_player: u8,
  variant: String,
  game_over: bool,
  winner: Option<u8>,
  winning_line: Option<Vec<usize>>,
  wrecking_ball_available: [bool; 2],
  heavy_available: [bool; 2],
  flip_available: [bool; 2],
  flipped: bool,
  hidden_rows: Option<std::ops::RangeInclusive<u8>>,
  last_event: Option<String>,
}

#[derive(serde::Serialize, serde::Deserialize, Clone, Copy, PartialEq)]
pub enum DropFourPieceKind {
  Normal,
  WreckingBall,
  Heavy,
}

#[derive(serde::Serialize, serde::Deserialize, Clone, Copy)]
pub struct DropFourPiece {
  owner: u8,
  kind: DropFourPieceKind,
}
```

Implementation notes:

- Use a 7x6 board with deterministic index helpers for column, row, neighbors, and gravity compaction.
- Check wins after every board mutation, including explosions, popouts, crushes, and flips.
- If a mutation creates simultaneous lines, define the active player as the winner unless tests justify a draw rule.
- Keep hidden lower-half state private in Battleship Drop while still enforcing all rules server-side.
- Emit `last_event` for major physics moments such as detonation, popout, flip, blind reveal, and crush.

### Backend Actions

Client actions should stay inside `GameAction`.

```json
{ "game": "DropFourMove", "column": 3, "piece": "normal" }
```

```json
{ "game": "DropFourPopOut", "column": 2 }
```

```json
{ "game": "DropFourFlip" }
```

Validation:

- Reject invalid columns and full-column drops.
- Reject popout when the bottom token is not owned by the active player.
- Reject second use of one-time Wrecking Ball, Heavy, or Flip powers.
- Re-compact affected columns after every removal or flip.
- Never reveal Battleship Drop hidden cells to either player until they rise above the screen or the game ends.

### Variant Rules

#### Classic

- Standard vertical four-in-a-row.
- Drop one token into any non-full column.
- First horizontal, vertical, or diagonal four-token line wins.

#### Wrecking Ball

- Each player has one marked Wrecking Ball token.
- The token drops like a normal token, then detonates immediately.
- Remove the Wrecking Ball and all adjacent tokens in the eight neighboring directions.
- Apply gravity after the blast so tokens above holes fall into new gaps.
- Check whether the resulting board creates a win.

#### PopOut

- On a turn, a player may either drop normally or remove one of their own tokens from the bottom row.
- Removing a bottom token makes that column drop by one slot.
- PopOut can break an opponent line or slide a player's own pieces into a new four-token line.

#### Gravity Flip

- Each player has one Flip Token power.
- Instead of dropping a token, the active player may flip the whole grid upside down once.
- Rebuild every column under the inverted gravity direction and then check for wins.
- Track `flipped` for UI orientation and future move physics.

#### Battleship Drop

- The lower half of the grid is hidden from both players.
- Players drop normally and must remember where pieces land behind the screen.
- State sent to clients masks hidden cells but still shows visible top-half cells.
- If a column stack reaches above the screen, visible cells render normally.

#### Heavy Token

- Each player has one Heavy token.
- When dropped into a column, it crushes and removes the token immediately beneath it, then takes that slot.
- Heavy cannot crush another Heavy token.
- After the crush, compact the column and check for wins.

### Frontend Implementation

Add:

- `frontend/src/components/DropFourBoard.tsx`
- `frontend/src/components/drop-four.module.css`
- `frontend/src/app/games/drop-four/page.tsx`
- `frontend/src/app/games/drop-four/[variant]/page.tsx`

UI requirements:

- Column-select controls first; drag/drop can be added later.
- Show available one-time powers as clear controls near the board.
- Animate gravity compaction enough to make explosions, popouts, flips, and crushes understandable.
- Mask hidden Battleship Drop cells with a clean screen layer.
- Use `GameFrame` for room, score, player strip, leave, and rules layout.
- Keep the board at a stable 7:6 aspect ratio on desktop and mobile.

Metadata:

- Add Drop Four Chaos to `frontend/src/lib/gameMetadata.ts` after the backend route exists.
- Include variants: `classic`, `wrecking-ball`, `popout`, `gravity-flip`, `battleship-drop`, `heavy-token`.
- Add `drop_four` to route mapping and SocialDock invite choices through catalog metadata.

### Drop Four Definition of Done

- Classic drop-and-win rules are covered by backend tests.
- Wrecking Ball explosion removes adjacent tokens and applies gravity deterministically.
- PopOut validates ownership of the bottom token and recomputes wins after the column drops.
- Gravity Flip is one-time per player and preserves token ownership while inverting the board.
- Battleship Drop masks hidden cells in `state_for_player`.
- Heavy Token crushes exactly one non-heavy token underneath it.
- Frontend renders all variant states without layout shifts on mobile.
